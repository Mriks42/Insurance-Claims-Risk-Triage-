ABSTRACT

We present an end-to-end insurance fraud triage system trained on two heterogeneous
datasets: the Vehicle Insurance Fraud Detection dataset (15,420 automotive claims,
5.99% fraud rate) and the Medicare Provider Fraud dataset (558,211 claims across
5,410 providers, 9.35% fraud rate). The primary model — XGBoost with Optuna Bayesian
tuning — achieves a Validation PR-AUC of 0.3223 (+28% over baseline) and a Test
PR-AUC of 0.2443 on automotive claims, concentrating fraud at 32.5% in the top 5%
of flagged claims (5.4x enrichment) and yielding an estimated net benefit of $868,400
(ROI: 15.1x). A cross-domain model trained on Medicare data achieves Test PR-AUC of
0.6869 with 8.9x SIU enrichment, validating methodology generalizability. The pipeline
includes SHAP explainability, Retrieval-Augmented Generation (RAG) triage briefs,
fairness analysis, drift monitoring, and a live 8-page Streamlit dashboard deployed
on Hugging Face Spaces.

================================================================================
1. INTRODUCTION
================================================================================

Insurance fraud costs the U.S. industry an estimated $40 billion annually [1]. Manual
review of every claim is infeasible at scale — insurers need an automated triage system
that concentrates investigator effort on the highest-risk claims while approving
low-risk claims automatically.

This project builds a complete fraud triage pipeline addressing three core challenges:
(1) accurate fraud risk scoring on severely imbalanced datasets, (2) explainable,
policy-grounded predictions that non-technical investigators can act on, and
(3) production-ready deployment with monitoring, fairness guarantees, and full
experiment reproducibility.

A critical finding during development was that the original notebook included
PolicyNumber as a model feature — a row identifier with 15,420 unique values across
15,420 rows. This caused artificial PR-AUC inflation from 0.25 to 0.79. All results
reported here use the corrected pipeline with PolicyNumber excluded.

================================================================================
2. DATA SOURCES AND ANALYSIS
================================================================================

2.1 Primary Dataset — Automotive Insurance

The fraud_oracle.csv dataset [2] contains 15,420 automotive insurance claims with
33 columns. The target FraudFound_P is binary with a 5.99% fraud rate (923 positive
cases). Data is split 80/10/10 stratified by target: train (12,336), validation
(1,542), and test (1,542). The validation set is used exclusively for model selection;
the test set is touched once for final honest evaluation.

Key features include: AccidentArea, VehicleCategory, BasePolicy, Fault,
PoliceReportFiled, WitnessPresent, AgentType, Days_Policy_Accident, and
NumberOfSuppliments.

2.2 Secondary Dataset — Medicare Provider Fraud

The Medicare Provider Fraud dataset [3] consists of four CSV files: provider labels
(5,410 providers), inpatient claims (40,474 records), outpatient claims (517,737
records), and beneficiary demographics (138,556 records). The target PotentialFraud
is binary at the provider level with a 9.35% fraud rate (506 of 5,410 providers).

Data integration: The four files are joined on Provider ID. Claim-level data is
aggregated to provider-level features via groupby (count, mean, sum, nunique).
Missing values from providers absent in a given file are filled with zero. The
resulting feature matrix has 5,410 rows and 22 features. Label encoding converts
"Yes"/"No" to binary 1/0.

2.3 Data Validation

A Pandera schema validation layer enforces ten checks on the automotive dataset before
any processing: row count > 100, no duplicate rows, no missing values in key columns,
fraud rate < 50%, age range 16-100, deductible validity, binary target, and valid
categorical values. One check fails on the raw data: 320 rows contain Age = 0, a
placeholder for unknown age. The pipeline proceeds with a warning.

2.4 Exploratory Data Analysis

EDA on the automotive dataset reveals: claims with no police report have a 2.1x higher
fraud rate; external agent claims show 1.8x higher fraud rate; sport vehicle claims
show 1.6x higher fraud rate; claims filed within 7 days of policy inception show 3.2x
enrichment. These patterns directly inform the guideline-grounded feature engineering.

On the Medicare dataset, providers with 500+ claims show a 51.8% fraud rate vs. the
9.4% baseline — systematic high-volume billing is the dominant fraud signal.

================================================================================
3. FEATURE ENGINEERING
================================================================================

We engineer 41 features from 31 raw automotive columns across six categories:

1. Ordinal encoding (13) — string-range columns converted to numeric midpoints
2. Time-based (3) — WeekGap, circular MonthGap, SameDayOfWeek
3. Binary risk flags (6) — NoPoliceReport, NoWitness, PolicyHolderFault,
   YoungDriver, HasPastClaims, WeekendAccident
4. Interaction features (5) — Age_x_Deductible, Fault_NoPolice, PriceToDeductible,
   Age_x_PastClaims, Cars_x_Supplements
5. Guideline-grounded flags (7) — derived directly from fraud guideline documents:
   Liability_NoPolice, HighValue_Liability, Sport_YoungDriver, VeryEarlyClaimFlag,
   EarlyClaimFlag, HighSupplements, ExternalAgent_NoPolice
6. Composite (1) — RiskFlagCount (sum of 14 binary indicators)

For Medicare, 22 provider-level features are derived from aggregated claims: total/
average reimbursement amounts, claim counts, unique patient and physician counts,
inpatient ratio, and beneficiary chronic condition averages.

================================================================================
4. METHODOLOGY
================================================================================

4.1 Preprocessing Pipeline

A scikit-learn ColumnTransformer applies median imputation and standard scaling to
numeric features, and one-hot encoding to categorical features. The transformer is
fit on the training set only and applied to validation and test sets to prevent
leakage. After transformation, the automotive feature matrix has 90 columns.

4.2 Baseline Models

Three baseline models are trained: Logistic Regression (L2, class_weight='balanced'),
XGBoost (eval_metric='aucpr', early stopping at 50 rounds), and LightGBM (early
stopping at 50 rounds). PR-AUC is used as the primary metric throughout — it is
appropriate for imbalanced classification where ROC-AUC can be misleadingly optimistic.

TABLE 1: Base Model Comparison (Validation Set)
-------------------------------------------------
Model                    PR-AUC   ROC-AUC   Prec@5%
XGBoost                  0.2518   0.8346    0.2857
LightGBM                 0.1846   0.8097    0.2208
Logistic Regression      0.1677   0.8108    0.1818
-------------------------------------------------

4.3 Bayesian Hyperparameter Optimization

XGBoost and CatBoost are tuned independently using Optuna's Tree-structured Parzen
Estimator (TPE) [4] — a Bayesian optimization algorithm that builds a probabilistic
model of the objective function and samples from regions likely to improve it,
outperforming random or grid search. Each study runs 20 trials with 3-fold stratified
cross-validation per trial (objective: mean PR-AUC), subject to a 300-second
wall-clock timeout.

4.4 Out-of-Fold Stacking Ensemble

An OOF stacking ensemble combines XGBoost (Optuna) and CatBoost (Optuna) as base
learners with Logistic Regression as the meta-learner. Base learner predictions are
generated using 5-fold cross-validation to avoid target leakage into the meta-features.

4.5 Isotonic Calibration

The best model's predicted probabilities are calibrated using isotonic regression on
the validation set, ensuring that predicted probabilities are reliable estimates of
actual fraud likelihood.

4.6 Validation Strategy

Model selection is performed exclusively on the validation set. The test set is used
once, after the best model is selected, to report honest generalization performance.
5-fold cross-validation on the training set provides an additional stability estimate:
CV PR-AUC = 0.2621 ± 0.0248.

6. CROSS-DOMAIN ANALYSIS — MEDICARE
================================================================================

6.1 Medicare Model Performance

TABLE 4: Cross-Domain Model Comparison
----------------------------------------
Metric              Auto              Medicare
Val PR-AUC          0.3223            0.7874
Test PR-AUC         0.2443            0.6869
Val ROC-AUC         0.8595            0.9646
SIU Fraud Rate      32.5%             82.9%
SIU Enrichment      5.4x              8.9x
CV PR-AUC           0.262 ± 0.025     0.679 ± 0.037
----------------------------------------

The Medicare model achieves significantly higher PR-AUC for three reasons:
(1) Stronger fraud signal — Medicare fraud is systematic overbilling across hundreds
    of claims, making TotalReimbursed (SHAP = 1.131) a dominant predictor.
(2) Aggregation amplifies patterns — provider-level features remove individual claim
    noise and amplify systematic billing behavior.
(3) Different fraud mechanism — Medicare fraud is a repeated business operation,
    while auto insurance fraud is a one-time opportunistic event.

6.2 Key Cross-Domain Finding

The top SHAP features are completely different across domains:
  - Auto:     Fault (0.823), Liability_NoPolice (0.546) — claim characteristics
  - Medicare: TotalReimbursed (1.131), TotalInpatientAmt (0.288) — billing volume

================================================================================
7. FAIRNESS, MONITORING, AND TEMPORAL ANALYSIS
================================================================================

7.1 Fairness Analysis

The 80% disparate impact rule is applied across sex, age group, and marital status.
The model flags males at ~22% vs. females at ~12%, yielding a disparate impact ratio
of 0.574 (below the 0.80 threshold). This may reflect genuine fraud patterns or proxy
discrimination via correlated features such as VehicleCategory and AgentType,
warranting further investigation before production deployment.

7.2 Model Monitoring

The test set is split into 6 time-ordered batches to simulate production monitoring.
Feature distribution drift is detected using the Kolmogorov-Smirnov test (with
Evidently as an optional enhanced backend). Batch 5 shows drift in 14.3% of numeric
features, flagging a potential distribution shift that would warrant model retraining
in production.

7.3 Temporal Analysis

Month-by-month evaluation reveals significant performance variation: PR-AUC ranges
from 0.11 (November) to 0.71 (December), suggesting seasonal fraud patterns.
Precision@5% drops to 0 in October and November, indicating months where fraud is
not concentrated at the top of the risk ranking.

================================================================================
8. RAG PIPELINE AND PRODUCTION ENGINEERING
================================================================================

8.1 RAG Triage Briefs

The RAG pipeline indexes 4 internal fraud guideline documents (56 chunks) using
ChromaDB [5] with all-MiniLM-L6-v2 sentence embeddings. For each claim, a retrieval
query is constructed from claim attributes and SHAP reason codes. The top-5 relevant
passages are retrieved and passed to GPT-4o-mini [6] to generate a natural language
triage brief with citations. A structured template fallback operates without an API key.

8.2 Pipeline and Experiment Tracking

A single train.py entry point orchestrates all five pipeline steps with MLflow nested
run logging: full_pipeline (parent) logs dataset statistics and runtime; base_modeling
logs dataset sizes and best base model PR-AUC; model_improvement logs all model
metrics, Optuna parameters, business ROI, and the best model .joblib artifact.

8.3 Testing and CI/CD

60+ pytest tests cover feature engineering correctness, data preprocessing, modeling
utilities, and the RAG pipeline. Two GitHub Actions workflows run on every push:
tests.yml blocks deployment on test failure; deploy.yml pushes to Hugging Face Spaces.
The application is containerized using Docker and deployed live at:
https://huggingface.co/spaces/Mriks/fraud-triage

================================================================================
9. CONCLUSIONS AND RECOMMENDATIONS
================================================================================

This project demonstrates that a well-engineered fraud triage system delivers
substantial business value across multiple insurance domains. Key contributions:

1. Data leakage detection — identifying and correcting PolicyNumber leakage that
   inflated PR-AUC from 0.25 to 0.79.
2. Two heterogeneous datasets — automotive insurance (15,420 claims) and Medicare
   provider fraud (558,211 claims), demonstrating cross-domain methodology
   generalizability.
3. Guideline-grounded features — 7 features derived from fraud documentation that
   rank among the top SHAP drivers.
4. Honest evaluation — strict train/val/test separation with the test set touched
   once, yielding credible Test PR-AUC of 0.2443 (auto) and 0.6869 (Medicare).
5. Production readiness — MLflow tracking, 60+ tests, CI/CD, Docker deployment,
   and live Hugging Face hosting.

Recommendations:
(1) Investigate the sex disparate impact ratio (0.574) before regulatory submission.
(2) Retrain when batch drift monitoring detects distribution shift.
(3) Impute Age = 0 records with the median age.
(4) Expand the training dataset — the 923 positive automotive cases limit the model's
    ability to learn rare fraud patterns; additional labeled data would likely improve
    Test PR-AUC substantially.
